request/response schemas and examples.

This document focuses on:
- API philosophy
- Resource design
- Versioning
- Error handling
- GitHub App integration flow
- Authorization model

# API Principles

- REST-style resource-oriented APIs
- Predictable URL structure
- Stateless requests
- JSON request/response
- UTC timestamps (ISO-8601)
- Stable pagination
- Idempotent operations where applicable

---

# API Versioning

Current version:

```text
/api/v1
```

Breaking changes require a new API version.

---

# Authentication

DevLens uses **GitHub App** as the primary integration.

Authentication of DevLens users and authorization inside DevLens are separate concerns.

GitHub installation tokens are generated by the backend and must never be exposed to the frontend.

---

# Authorization

Typical roles inside DevLens may include:

- Owner
- Admin
- Maintainer
- Viewer

The concrete role model used by each endpoint is defined by `openapi.yaml`.

---

# GitHub App Flow

```text
Frontend
    |
Connect GitHub
    |
Backend
    |
GitHub App Installation
    |
Installation Callback
    |
Store Installation
    |
Discover Accessible Repositories
    |
User Selects Repositories
    |
Initial Sync
    |
Dashboard
```

Frontend never communicates with GitHub APIs directly.

```text

```

Refer to `openapi.yaml` for the authoritative list.

---

# Error Model

Every error should contain:

- code
- message
- requestId (when available)
- details (optional)

Validation errors should identify the offending field when possible.

---

# Pagination

Collection endpoints should use consistent pagination.

Recommended fields:

- page
- pageSize
- total
- items

If cursor pagination is introduced later, it should be documented in OpenAPI.

---

# Idempotency

The following operations should be idempotent where appropriate:

- webhook ingestion
- sync job creation (using idempotency keys)
- retry operations

---

# Metrics APIs

Metrics endpoints return calculated data.

They must not trigger GitHub synchronization during the request.

If data is unavailable, return the contract defined in `openapi.yaml` instead of calculating live.

---

# Webhooks

Webhook handlers should:

1. Validate signature
2. Persist delivery log
3. Prevent duplicate processing
4. Enqueue background work
5. Return quickly

Heavy processing belongs to workers.

---

# Long-running Operations

Initial sync and rebuild operations are asynchronous.

Clients should observe progress using Sync Job APIs.

---

# Naming

- Resources use plural nouns.
- Path parameters use `{resourceId}`.
- JSON fields use camelCase if defined by OpenAPI.
- Internal database naming is independent from API naming.

---

# Definition of Done

Before adding a new endpoint:

- Business flow exists
- OpenAPI contract updated
- Backend implementation completed
- Tests added
- Frontend integration verified

This document intentionally avoids duplicating endpoint schemas.
Always consult `openapi.yaml` for the definitive API contract.
